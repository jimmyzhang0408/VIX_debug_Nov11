# Olympus XRF API
Overview and introduction.

Last updated 22-March 2021 


## General Description

The Olympus XRF API is a network socket-based interface that can be used by third-party developers to interface their own software with a Vanta instrument. It relies upon JSON messages sent between the instrument and the client to configure, start, and view the results of XRF tests conducted by the instrument. Since the API is socket-based, there are no header files to include nor any libraries to link to.

In order to **control** an instrument remotely, either a client must be connected to the instrument via the OTG port, or both the client and the instrument need to be on the same LAN. In addition, to be a controller, no user can be logged in locally to the instrument; the instrument software must be displaying the Welcome screen.

## Sample Codes

Sample C++ code has been provided for a simple application which does the following:

- Connects to a Vanta instrument
- Logs in as an administrative user
- Starts a test
- Display status messages returned by the instrument

The sample application uses the Qt library to ease the WebSocket client implementation as well as to serialize JSON commands and parse JSON responses from the instrument.  To build and run this sample application requires Qt Creator.  This can be downloaded from the following link https://www.qt.io/download 

However, use of Qt is not required: any WebSocket / JSON serialization library will suffice.

A second sample is provided in Python showing how to create a WebSocket client that can connect to a Vanta, run tests and show results.  

> Note: The C++ sample application assumes that the instrument is connected to the client PC via the OTG port, but if the instrument is connected to a WiFi network and the IP address is known, it could be controlled wirelessly as well. The Python example can connect to units via USB or IP address based on the configuration file.

## Operation of the C++ Sample Application

The sample application creates an instance of the VantaCommunicator class, which is responsible for connecting to the instrument and parsing its responses. It then calls the **start()** method, which connects to the instrument via an instance of the WebSocketClient class and starts the application event loop. 

The WebSocketClient class manages the connection to the instrument and handles event generated by the underlying QWebSocket object. Once the connection to the instrument has been established, **WebSocketClient::onConnected()** will be called. This handler sends a simple text message ("Hi i am a controller") to the instrument that identifies the PC client as a controller. 

> Note: this command is sent as text, where all other future commands are sent using binary mode. This string is case sensitive, and has to be sent exactly as shown with a small 'i'

The instrument will respond with one of the following messages:

- "Server ready to receive commands."
  - The connection is established and the instrument is ready to receive commands.
- "Rejecting connection. Device being controlled by <ipAddress>"
  - The instrument is already being controlled remotely by a client at <ipAddress>.
- "Rejecting connection. User is Logged In."
  - A user is currently logged into the instrument.

The response is received in **WebSocketClient::onTextMessageReceived()** and passed to **VantaCommunicator::status()**. If the response indicates that the instrument is ready, a login command is constructed using the MessageFactory class and sent to the instrument.

Further responses from the instrument are handled by **VantaCommunicator::messageResponse()**. When a response to the login command is received, a Start Test command is sent, which starts an XRF test on the instrument.

## Operation of the Python Sample Application

The sample python application creates a websocket and then uses this in a listening thread which simple prints out the responses received over the connection.

**vanta_create_connection(ws)** function is called to initialize the connection. It connects to the IP address (192.168.7.2) and port (7860) which corresponds to a Vanta connected by USB. If the connection is successful it issues the command **"Hi i am a controller"**.

> Note: this command is sent as text, where all other future commands are sent using binary mode. This string is case sensitive, and has to be sent exactly as shown with a small 'i'

If there are no other users connected to the system the vanta will respond with the string "Server ready to receive commands."

If the connection was created successfully, it is now possible to send further commands and receive responses.  The system will actually send some responses automatically, to reflect status changes in the system. Since these responses should be processed the sample application starts a thread which uses **vanta_listen(ws)** to wait for responses.

This sample implements only 2 commands to give an example of how command would be sent. The most important thing to not is that the **vanta_send_command()** function uses the **ws.send_binary**(command) function to send the data over the connection. If the command is sent as text it is not correctly interpreted by the Vanta.

## API Message Structure

All messages sent to and returned from the instrument are in the form of json. You can find more information about json here (https://www.json.org/json-en.html)

### Commands

Commands are sent from the client to the instrument. They consist of a **command ID**, an optional **packet ID**, and a set of parameters that are specific to the **command ID** that is being sent. For example, consider the Login command:

```json
{
    "commandId": 301,
    "id": 1234,
    "params": {
        "userId": "Administrator",
        "password": "0000"
    }
}
```

The command ID is **301**, which identifies this message to the instrument as a Login command. The **"id"** field is optional, and can be any integer – it is typically used by a client to identify the corresponding response (see below). The parameters include the user’s ID ("Administrator" in this case), and password.

### Responses

Responses are sent from the instrument to the client after receiving a command. They will always include the **command ID** and optional **packet ID** that was sent in the corresponding command, so if a client were to attach a unique packet ID to each command, it would be able to marry up any response to the command that generated it. An example response is below:

```json
{
    "commandId": 301,
    "id": 1234,
    "params": {
    }
}
```

The **command ID** is **301**, which identifies this response as being a response to a Login command. The packet ID ("id") is the same as the one passed in the Login command by the client. There are no parameters to this response.

### Notifications

Notifications are sent asynchronously from the instrument to the client to signal certain events to the client – for example, that a chemistry result has been calculated. The message structure of a notification is identical to that of a command or response – only a **command ID** of **403** distinguishes it from any other message.

Since notifications are not sent in response to a command from the client, the **"id"** field instead identifies the type of notification. For example, consider the SystemStatus notification:

```json
{
    "commandId": 403,
    "id": 100,
    "params": {
        "systemStatus": "Ready",
        "info": ""
    }
}
```

The **command ID** of **403** identifies this message as a notification, the **"id"** field of **100** identifies it as a **SystemStatus** notification, and the parameters include the overall status **("Ready")** as well as more detailed information (none in this case).
